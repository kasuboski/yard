Why Chute Replaces Bash Design

The inspiration comes from flue's agent harness — it gives the LLM direct shell access via local(). Powerful, but dangerous. Chute replaces bash with a sandboxed, typed, capability-declared scripting language.

⚡ Flue approach: Bash access

  • Shell injection risks
  • Unbounded execution (while loops)
  • No capability audit trail
  • LLM can do anything the process can
  • Raw power, maximum flexibility
  • Familiar to LLMs (bash is well-known)

◆ Chute approach: Typed queries

  • Effects declared upfront (auditable)
  • Guaranteed halting (no loops, gas limits)
  • Typed results (declared return shapes)
  • Path sandboxing built in
  • Full audit trail of every effect
  • Type checker serves as firewall

When the LLM wants to explore a repo, it doesn't write cat src/main.gleam. It writes a chute program that declares what it wants to read and declares what shape it expects back.

The Outer Chute Actor Chute

The actor is the deterministic orchestrator — the "what" of the workflow, never the "how". It declares effects for each capability it needs and chains them with pipelines.

chute — actors/triage.chute 
// 1. Verbs — declared capabilities
effect clone_repo(url: String, ref: String) -> Result(Workspace, Error)
effect run_agent(request: AgentRequest) -> Result(String, Error)
effect post_comment(repo: String, issue: Int, body: String) -> Result(Nil, Error)

// 2. Nouns — entrypoint envelope
pub fn main(env: {
  action: String,
  issue: { number: Int, title: String, body: String },
  repository: { full_name: String, clone_url: String }
}) -> Result(Nil, Error) {

  case env.action == "opened" {
    True -> {
      env.repository.clone_url
      |> perform clone_repo("main")
      |> result.try(fn(ws) {
        perform run_agent({
          workspace: ws,
          task: "Analyze this issue for severity",
          model: "anthropic/claude-opus-4-7",
          skills: ["triage"],
        })
      })
      |> result.try(fn(report) {
        perform post_comment(
          env.repository.full_name,
          env.issue.number,
          report,
        )
      })
    }
    False -> Ok(Nil)
  }
}

The key insight: this program is pure computation + declared intents. It doesn't decide how to triage — it says what needs to happen and in what order. The host handles the "how".

The runner effect loop

This is the core host component — a simple loop over ballast's existing yield/resume protocol.

pseudocode 
fn run_loop(program, env, gas, handlers) {
  case ballast.start_program_with_env(program, env, gas) {
    EvalDone(value, gas)     -> Ok(value)               // Program finished
    EvalError(error)         -> Error(error)            // Runtime error
    Yielded(effect, args, cont, gas) ->                // Hit a perform!
      case dict.get(handlers, effect) {
        Ok(handler) ->
          case handler(effect, args) {
            Ok(result) -> run_loop_resume(cont, result, gas, handlers)
            Error(err)  -> Error(err)
          }
        Error -> Error("Unknown effect")
      }
  }
}

Agent Output Pig

The run_agent effect returns Result(String, Error) — the agent's final response as a plain string. The agent's skill/prompt instructs it on how to format its output (markdown report, plain text summary, etc). The chute program just passes the string through to wherever it needs to go.

The effect declaration

effect run_agent(request: AgentRequest)
  -> Result(String, Error)

What pig returns

**Severity:** high
**Reproducible:** true

### Summary

`src/parser.gleam:42` when the config
object has no `name` field.

### Suggested Fix
Add a null check before accessing
`config.name`.

pig.run() already returns the assistant's final message text. The agent's skill tells it to format as markdown. The chute program passes this string directly to post_comment.

How it works

The host starts a pig agent session. The agent explores the workspace via the chute_exec tool, then returns its final response. The host wraps that response as a StringVal and resumes the outer chute program:

pseudocode — host runtime 
// When handling run_agent effect:
fn run_agent_handler(effect_decl, args) {
  // 1. Extract task details from the request record
  let request = args[0]   // RecordVal({ workspace, task, model, skills })

  // 2. Start pig agent with chute_exec tool
  let config = pig.new(provider_for_model(request.model))
    |> pig.with_tool(chute_exec_tool)
    |> pig.with_skills(request.skills)

  // 3. Run agent — it explores, reasons, returns final text
  let assert Ok(agent) = pig.start(config)
  let result = pig.run(agent, request.task)

  // 4. Final message text → StringVal, resume outer chute
  let message = result.assistant_message.content  // plain string
  ballast.resume(cont, StringVal(message))
}

Why string, not structured data?

In most scenarios the chute program is pure plumbing — it delivers the agent's output to its destination (post a comment, send a message, write a file). The agent owns the formatting. The chute program doesn't need to understand or branch on the content.

If a future scenario needs the chute program to branch on agent output (e.g., "if severity is critical, also send a Slack alert"), the effect return type can be upgraded to a structured record. The host would then extract a schema from the chute type and use it to parse the LLM's response. But that's a power-up for later — string handles today's use cases cleanly.

Testing Actors Testability

The chute runner is just a loop over ballast's yield/resume with a dict of handler functions. In tests, you swap real handlers for deterministic fakes. The entire actor runs in microseconds — no git clone, no pig agent, no GitHub API.

The test handler pattern

Each test handler is a pure function: (effect_name, args) → Result(Value, RuntimeError). It inspects the effect name and args, asserts what it expects, and returns a canned response.

gleam — test/actors/triage_test.gleam 
import chute
import ballast
import ballast/value

// Load the real actor — same source that runs in production
const actor_source = "actors/triage.chute"

fn run_actor(handlers, env, gas) {
  let assert Ok(program) = chute.parse(actor_source)
  let program = chute.desugar(program)
  runner.run_loop(program, env, gas, handlers)
}

// ── Test: happy path, issue opened ──────────────────────────────

pub fn triage_opened_issue_test() {
  let handlers = dict.from_list([
    // When the actor clones the repo, return a fake workspace ref
    #("clone_repo", fn(_name, args) {
      let assert [StringVal(url), StringVal(ref)] = args
      // Verify the actor passes the right args
      let assert url == "https://github.com/org/repo.git"
      let assert ref == "main"
      Ok(StringVal("ws:test-workspace"))
    }),

    // When the actor runs the agent, return a fake markdown report
    #("run_agent", fn(_name, args) {
      let assert [RecordVal(fields)] = args
      let fields_dict = dict.from_list(fields)
      let assert Ok(StringVal(task)) = dict.get(fields_dict, "task")
      let assert task == "Analyze this issue for severity"
      Ok(StringVal("## Triage Report\n\n**Severity:** low"))
    }),

    // When the actor posts a comment, verify the body contains the report
    #("post_comment", fn(_name, args) {
      let assert [
        StringVal(repo),
        IntVal(issue_num),
        StringVal(body),
      ] = args
      let assert repo == "org/repo"
      let assert issue_num == 42
      let assert string.contains(body, "## Triage Report")
      Ok(OkVal(NilVal))
    }),
  ])

  // Build the webhook payload (what GitHub would send)
  let env = RecordVal([
    #("action", StringVal("opened")),
    #("issue", RecordVal([
      #("number", IntVal(42)),
      #("title", StringVal("Crash on startup")),
      #("body", StringVal("App crashes when launched with no config")),
    ])),
    #("repository", RecordVal([
      #("full_name", StringVal("org/repo")),
      #("clone_url", StringVal("https://github.com/org/repo.git")),
    ])),
  ])

  // Run the real actor with fake handlers
  let result = run_actor(handlers, env, 50_000)

  // Verify final result
  let assert Ok(OkVal(NilVal)) = result
}

// ── Test: clone failure propagates ─────────────────────────────

pub fn triage_clone_failure_test() {
  let handlers = dict.from_list([
    #("clone_repo", fn(_name, _args) {
      // Simulate a git clone failure
      Ok(ErrorVal(StringVal("clone failed: auth error")))
    }),
  ])

  let env = RecordVal([ /* opened action, same as above */ ])
  let result = run_actor(handlers, env, 50_000)

  // result.try short-circuits — run_agent and post_comment never called
  let assert Ok(ErrorVal(StringVal("clone failed: auth error"))) = result
}

// ── Test: unknown effect causes error ──────────────────────────

pub fn triage_unknown_effect_test() {
  let handlers = dict.new()  // empty — no handlers registered
  let env = RecordVal([ /* opened action */ ])
  let result = run_actor(handlers, env, 50_000)

  // Runner returns error for unhandled effect
  let assert Error(RuntimeError("Unknown effect: clone_repo")) = result
}

Why this works

What's being tested

  • The real actor source code (not a mock)
  • Control flow branching (opened vs closed)
  • Pipeline chaining (result.try short-circuits)
  • Effect argument construction
  • Error propagation from handlers

What's faked

  • git clone → returns canned workspace ref
  • pig agent → returns canned markdown string
  • GitHub API → asserts args, returns Ok(Nil)
  • Zero IO, zero network, runs in <1ms
  • Fully deterministic, no flakiness

This is the same pattern as ballast's existing effect tests — the runner is just a loop over yield/resume. The only new thing is the handler dict that lets you register named effect implementations. The test handlers are pure Gleam functions, so they're trivially composable: share common handlers between tests, layer on assertions, or build a handlers_for("triage") helper that returns a standard set with overrides.

Design Decisions Open Questions

Click each decision to expand the reasoning.

▶
Workspace identity: explicit or implicit?
Answer: Implicit
Inner chute programs don't reference the workspace by ID. The host binds read_file/list_dir/grep to the current workspace automatically. This keeps the LLM's programs simple and lets the host enforce path sandboxing without the LLM needing to think about it. Paths are relative to the repo root.
▶
How does the host know which actor to run for a webhook?
Answer: Configured routes at startup
No auto-discovery. The host maps webhook paths to chute actors explicitly in runtime setup code: routes: { "/webhook/github" → "actors/triage.chute" }. Simple, explicit, auditable. Can add pattern matching later.
▶
How does the agent return results to the chute program?
Answer: Plain string — pig.run() returns the final message text
The run_agent effect returns Result(String, Error). pig.run() already returns the assistant's final message as text. The agent's skill instructs it to format the output (markdown report, summary, etc). The chute program passes the string directly — e.g., post_comment(repo, issue, report) where report is just the markdown string. If a future scenario needs the chute to branch on agent output fields, the return type can be upgraded to a structured record.
▶
Can one actor kick off multiple agents concurrently?
Answer: Yes, via task.dispatch_all
Chute already has task.dispatch_all for batching thunks. If the outer actor wraps multiple run_agent performs in thunks and dispatches them, the host runs multiple pig agents concurrently. Natural on BEAM — each pig agent is a separate process.
▶
Actor-to-actor communication?
Answer: send_message effect
A new effect send_message(actor: String, payload: Value) → Result(Nil, Error). The host routes it to another chute actor's runner. This is the actor model on top of chute + BEAM. Each actor is a BEAM process, messages are delivered via the host runtime.
▶
Should chute get workspace-specific stdlib functions?
Answer: Noted for later
Functions like path.join, path.basename, json.parse, json.stringify would help the LLM write better exploration programs. These are pure functions that fit naturally into chute's stdlib. Not blocking — can add when needed.
