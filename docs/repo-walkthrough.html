01 Executive summary

What this project is, in one screen.

LLMs write code linearly — top to bottom, left to right. Most languages fight that with nested scopes, early returns, and pyramids of doom. This project embraces it. Chute is a tiny pipeline-first language an LLM can generate correctly token-by-token. It has no loops, no recursion, and no direct I/O — so any program written in it is guaranteed to halt and cannot touch the outside world on its own.

Instead of doing I/O, a Chute program declares what it wants to do at the top of the file (effect charge_card(...)) and asks for it with perform. When the evaluator (Ballast) hits a perform, it doesn't call anything — it yields a data value describing the intent and pauses. Yard, the host runtime, sees that yield, does the real work (HTTP, DB, LLM call), and resumes the evaluator with the result. To the LLM the code looks synchronous; to the runtime it's a pure function.

The one-sentence mental model A Chute program is a deterministic recipe. Ballast cooks it but refuses to leave the kitchen. Yard is the waiter who carries each instruction ("charge the card") out to the real world and brings the result back.

Why this split exists

  • Safety by construction — untrusted LLM code runs in a sandbox that provably halts and provably cannot do I/O. Side effects are a host-controlled capability, not a language feature.
  • Static capability checks — before a program runs, the host scans its declared effects against an allow-list. A hallucinated effect delete_database() is refused before execution.
  • Observability for free — because every side effect is a yield/resume crossing the host boundary, the host can log, time, and checkpoint each one automatically.
  • Durability — that same boundary lets the host checkpoint each effect result, so a crashed run can resume without re-charging a card or re-calling an LLM.

02 The big picture

Three layers, one pipeline. Data and control flow left to right.

Chute
the language
Pipeline syntax an LLM generates. Parses source → AST → desugars pipelines → canonical S-expressions for transport. Static type-check + effect declaration scan.
━━━▶parse / desugar
Ballast
the evaluator
Pure functional, CPS tree-walker. Zero I/O. Gas counter = guaranteed halt. Hits perform → yields a value + continuation, waits to be resumed.
◀━━━▶yield / resume
Yard
the host runtime
Generic loop over Ballast's yield/resume. Dispatches each effect to a handler, emits structured events, checkpoints results, loads actors, fires cron triggers.
Read this first Each node is a separate Gleam package with a hard dependency arrow: chute ← ballast ← yard. The arrow is one-directional for good reason — the inner layers know nothing about the outer ones. Ballast never imports Yard; Chute never imports Ballast. This is what makes the sandbox boundary real and testable.

A pipeline-first language tuned for LLM token generation. No loops, no recursion, no imports — only declared effects.

Designed for linear generation

Data flows top-to-bottom through |> pipelines. No nested scopes, no early returns, no pyramids of doom — exactly the shape an LLM emits when writing left-to-right.

What a program looks like

a complete Chute actor (from the issue-triage example)
// 1. Verbs — declared capabilities (the only way to do I/O)
effect fetch_issue(repo: String, number: Int) -> Result(String, String)
effect run_agent(context: String, task: String) -> Result(String, String)
effect update_issue(repo: String, number: Int, comment: String) -> Result(Nil, String)

// 2. Nouns — a single env envelope is the only entrypoint
pub fn main(env: { repo: String, tracking_number: Int }) -> Result(Nil, String) {
  // 3. Linear pipeline + `let try` for error propagation
  let try issue = perform fetch_issue(env.repo, env.tracking_number)
  let try result = perform run_agent(issue, "summarise changes")

  // 4. Pattern match to branch (no if/else, no exceptions)
  case result {
    "NO_CHANGES" -> Ok(Nil)
    _ -> perform update_issue(env.repo, env.tracking_number, result)
  }
}

Why this matters for safety Two bans do the heavy lifting: no loops/recursion (iteration is list.map/filter/fold only) plus a gas counter in Ballast means every program provably halts. Combined with the effect firewall, an LLM cannot write code that hangs, recurses infinitely, or exfiltrates data through an unapproved channel.

06 Ballast — the sandbox

A pure functional evaluator. It cannot print, cannot open a file, cannot make a network call. It only evaluates expressions — and yields when it needs the outside world.

CPS evaluator

The sandbox boundary is perform

When Ballast hits perform charge_card(99.95) it returns a value — Yielded("charge_card", [99.95], <continuation>, gas) — not a side effect. The continuation is an opaque Gleam closure capturing "everything that happens next."

eval.gleam — CPS core
effect.gleam — EvalResult + Continuation
gas counter

Guaranteed halting by construction

Every eval call ticks a counter. Default budget 10,000 steps. Hit zero → GasExhausted. Even a list.fold over a huge list can't burn unbounded resources. No threads, no coroutines — just functions.

eval.gleam — tick() per call
value.gleam — RuntimeError

Every evaluation produces exactly one of three outcomes

ballast/src/ballast/effect.gleam
pub type EvalResult {
  EvalDone(value: Value, gas: Int)          // normal completion
  Yielded(                            // hit a `perform` — hand to host
    effect: String,                    //   "charge_card"
    args: List(Value),                //   [FloatVal(99.95)]
    continuation: Continuation,          //   opaque — resume() is the only op
    gas: Int)                         //   remaining budget
  EvalError(error: RuntimeError)        // non-recoverable
}

Why CPS instead of BEAM processes? The evaluator is pure — it returns values, the host decides how to drive it (sync loop, GenServer, distributed). Testing is trivial (no process setup). The continuation is just a Gleam closure. This purity is what later lets Yard checkpoint and resume a run across a crash.

Built-in stdlib (implemented inline in eval.gleam)

These are the only way to iterate — there is no while or for. task.dispatch_all batches thunks for concurrent effect dispatch. Full reference: knowledge/ballast.md.

07 Yard — the host runtime

The glue between Ballast's sandbox and the real world. The biggest layer — orchestration, observability, durability, scheduling, persistence, and a dashboard.

But the heart of Yard isn't yard.gleam — it's the runner: one function that every trigger, test, and inner program funnels through.

★ The runner — one loop to rule them all

yard/runner.gleam is the single place where Ballast's yield/resume cycle is consumed as a loop. It has zero knowledge of specific effects or triggers — effect names and trigger types are just strings. This is the load-bearing architectural decision: everything goes through runner.run(config), so observability and durability are baked in by construction.

runner.run(config)
▸emit ActorStarted · record start time
▼
▸ballast.start_program_with_env(program, env, gas) → first EvalResult
▼
▸loop on the EvalResult:

EvalDone → emit ActorCompleted, return Ok(value)

EvalError → emit ActorCompleted, return Error

Yielded(name, args, cont, gas) → the interesting case:

aDurability lookup — store.lookup(step, name). If a checkpoint exists, emit EffectReplayed, resume Ballast with the stored value (skip the handler entirely).
▼ no checkpoint
bemit EffectYielded · look up handler by name in config.handlers dict
▼
ccall the handler (name, args) → Result(Value, Error) — this is where real I/O happens
▼

▼
eballast.resume(cont, value) → next EvalResult · loop back to ▸
Everything calls the runner Webhooks, cron ticks, message routers, the chute_exec tool, and tests all build a RunConfig and call runner.run(config). A trigger is just code that translates an external stimulus into a RunConfig (right actor, env, handlers, trigger_type/source strings). Adding a trigger type requires zero changes to Yard.

Durability — surviving crashes without double-charging

This is Yard's newest and most subtle feature. A Chute run that crashes mid-way should resume without re-running side effects. The seam is the DurableStore passed in every RunConfig.

The two-level model

  1. Chute/Ballast effects — checkpoint each effect handler result keyed by "{step}:{effect_name}". On retry, replay stored values instead of calling handlers.
  2. Pig LLM turns — checkpoint each LLM response and tool result keyed by message index, so a crashed conversation resumes without re-calling the model.

Both run inside gabsurd (Absurd) Postgres tasks. Transparent to the Chute program and the LLM.

The principled error policy (ADR-0001)

lookup vs record — asymmetric by design lookup is best-effort — "not found" is the normal first-run case; a corrupt/missing checkpoint just falls through to fresh execution. record is a guarantee — a store failure surfaces and fails the Run, because silently losing a checkpoint breaks the durability promise invisibly.

This relies on the idempotent handler contract: handlers must be safe to run twice with the same inputs, because retry can double-execute the step whose checkpoint failed to save.

How it's wired

db.gleam takes gabsurd/client.Db (a Postgres connection pool). Entry points call client.start(db_url) to get a pool. The schema is applied by bin/postgres.sh, which runs pg_schema.sql + durable_schema.sql + Absurd's own schema. migrate() is a no-op — schema management is done at the container level.

Test helpers (testing.gleam) create a per-test pool, TRUNCATE the registry tables, run the test, then close the pool. idle_session_timeout=5s on Postgres reaps any leaked connections.

Editing the schema Edit sql/pg_schema.sql for registry table changes, or sql/durable_schema.sql for conversations/events. Re-run bin/postgres.sh to apply. Queries are hand-written in db.gleam using parrot/dev parameter types.

Scheduling — pg_cron (PostgreSQL-native)

Schedules live in PostgreSQL's cron.job table via the pg_cron extension. Each schedule fires absurd.spawn_task directly into a gabsurd queue — no OTP tick loop, no in-process state. Schedules survive BEAM restarts because they're database rows, not Erlang process state.

yard/src/yard/pg_cron.gleam — the scheduler API
// Schedule a recurring task

// List / cancel / unschedule all
pub fn list_jobs(db) -> Result(List(CronJob), CronError)

Security: cron handlers are namespace-scoped The Hermes agent's list_crons_handler filters to jobs with a hermes_ prefix, and cancel_cron_handler rejects non-hermes_ names. A Chute actor cannot discover or cancel unrelated database cron jobs.

Tests mock the pg_cron extension via cron_test_stub.sql. bin/postgres.sh applies this stub at container creation for local dev.

Handler registry — effects meet their implementations

Each agent declares effects in its Chute source and binds them to named handlers in the agent_handlers table (e.g. effect fetch_issue → handler http_get_handler). handler_registry.gleam maps those handler names to builder functions, and resolve_for_agent turns a row-set of bindings into the Dict(String, EffectHandler) the runner needs.

The dashboard UI

ui/server.gleam is a mist HTTP server started via yard.start_with_ui(). It queries PostgreSQL directly for runs, conversations, and events. Routes: / dashboard, /runs, /runs/:id, /conversations, /conversations/:id. HTML is server-rendered by ui/template.gleam; data fetched by ui/queries.gleam.

09 End-to-end flows

Trace a single run from trigger to result, and a crash-retry through durability.

Flow A — a webhook triggers a Chute actor

1Trigger adapter receives an HTTP request → parses body into a Value env, generates a run_id.
▼
2loader.load(source, path) — parse + desugar + SHA-256 hash of S-expression → LoadedActor.
▼
3Build RunConfig (program, env, gas, handlers dict, emit callback, trigger_type="webhook", store).
▼
4runner.run(config) — emit ActorStarted, hand program to Ballast.
▼
5Ballast yields Yielded("charge_card", [...], cont, gas).
▼
6Runner emits EffectYielded → looks up charge_card handler → calls it (real Stripe API call).
▼
7Runner emits EffectHandled → records result in store → ballast.resume(cont, tx_id).
▼
8Ballast evaluates more, eventually returns EvalDone → runner emits ActorCompleted, returns Ok(value).
▼
9Every event flowed: runner → dispatcher → :telemetry + JSONL session + Postgres yard_events (and pig_events for pig's agent-internal events when the bridge is enabled).

Flow B — a crash mid-run, then retry (durability)

First attempt (crashes after step 1)

1charge_card handler runs ✓ → result recorded as checkpoint "0:charge_card".
▼
2Ballast resumes, yields send_receipt…
▼
💥BEAM node crashes. Nothing recorded for step 1's send yet.

Retry (gabsurd reclaims the task)

1Runner starts fresh, yields charge_card at step 0.
▼
2store.lookup(0, "charge_card") → Ok(Some(stored)). Emit EffectReplayed. Handler NOT called again — no double-charge.
▼
3ballast.resume with stored value → yields send_receipt at step 1.
▼
4lookup(1, "send_receipt") → None (nothing stored). Runs the handler fresh, records it. Run completes. ✓

The key insight: because Ballast is a pure CPS evaluator and the continuation is just a closure, "resume" is deterministic — replaying the same checkpoints always reaches the same point. The idempotent-handler contract covers the one window where double-execution can still occur (step whose record failed before the crash).

10 Developer workflow

Everything runs through mise. The task definitions in mise.toml are the source of truth.

the commands you'll actually use
# one-time: install the toolchain (gleam, erlang, rebar3)
mise install

# the CI gate — MUST pass before every commit, no exceptions
mise run pre-commit        # = check + format + build + test across all projects

# run a single phase across all projects
mise run check   | mise run format | mise run build | mise run test

# scoped to one package
mise run chute:test    mise run ballast:check    mise run yard:build

# try the example apps
mise run hermes:run          # CLI agent demo
mise run hermes:gateway      # Telegram gateway (needs TELEGRAM_BOT_TOKEN)

# tests + durability need PostgreSQL
bin/postgres.sh             # starts docker, applies all schemas, sets idle_session_timeout
⚠ Environment for LLM features The examples and pig integration expect an OpenAI-compatible endpoint (defaults to local Ollama at localhost:11434/v1). Set OPENAI_COMPAT_BASE_URL, OPENAI_COMPAT_API_KEY, OPENAI_COMPAT_MODEL, and GITHUB_TOKEN as needed.

Code search (from AGENTS.md)

The repo recommends semble search "describe what it does" ./path for semantic lookup over grep, and semble find-related file.gleam line ./path to discover related code. Fall back to grep only for exhaustive literal matches.

11 Glossary

The project's controlled vocabulary (canonicalised in CONTEXT.md). Using these terms correctly matters — they carry precise meaning.

TermMeansAvoid saying
ChuteThe pipeline-first language for LLM generation.script, DSL, config
BallastThe pure functional evaluator that cannot touch the outside world.interpreter, VM, runtime
YardThe host runtime that loops over Ballast and wires it to the real world.server, platform, framework
ActorA loaded Chute program, identified by actor_path (where) + actor_hash (what code).agent, bot, worker
EffectA capability a Chute program declares & invokes via perform; the host decides what happens.function, command, API call
RunOne invocation of an Actor through the Yard runner.execution, session
CheckpointA stored effect result, keyed by position + name, enabling resume without re-executing side effects.snapshot, cache
ReplayFeeding stored checkpoints to Ballast instead of calling handlers, so side effects aren't repeated on retry.restore, fast-forward
Idempotent handlerA handler safe to run twice with the same inputs — the contract that makes durability correct.pure function
